# Plan 02-02: Adaptive Dual-Station Console & Live Recipient Inbox Verification

## Objective
Deliver an intuitive, high-fidelity dual-station tactical operator console supporting seamless switching and concurrent side-by-side monitoring between Station Alpha (`endpoint-a`) and Station Bravo (`endpoint-b`) with zero state loss, verified recipient inbox polling against `GET /api/v1/endpoints/<id>/inbox` with emerald 3D seal badges, and a 1.5s adaptive polling engine throttled to 5.0s in background tabs.

### Truths
- Operator can toggle between "Single Console" and "Dual Split-Screen" views via a 3D tactical toolbar toggle without losing draft text, selected priorities, or message types.
- In Dual Split-Screen view, Station Alpha (`endpoint-a`) and Station Bravo (`endpoint-b`) render side-by-side concurrent columns with independent quick composers and live transmission feeds.
- The UI polls both `GET /api/v1/endpoints/endpoint-a/inbox` and `GET /api/v1/endpoints/endpoint-b/inbox`, verifying that messages physically reside in recipient SQLite storage.

- Clicking any message or inbox card smoothly opens the slide-out `MessageTelemetryDrawer.tsx` without disturbing the dual column layout.

<threat_model>
### T-02-02: Cross-Station Recipient Inbox Data Pollution
- **Threat:** Querying recipient inboxes without strict station identifier boundaries could leak or blend Station Alpha and Station Bravo private message tables.
- **Impact:** Breach of multi-endpoint operational compartmentalization and false verification reporting.
- **Mitigation:**
  - `StationConsoleColumn` binds queries strictly to its configured `stationId` (`endpoint-a` or `endpoint-b`).
  - `api.getInbox(endpointId)` ensures the path parameter is strictly URI-encoded and bounded to the target station.
  - Received messages are validated to match `recipient_endpoint_id === stationId`.

### T-02-03: Polling Race Conditions and Resource Exhaustion
- **Threat:** Unthrottled 1.5s polling across multiple endpoints in background tabs causes CPU thrashing, memory leaks, or stale responses overwriting newer optimistic states.
- **Impact:** Browser slowdown, battery drain, and UI state inconsistency.
- **Mitigation:**
  - Dynamic interval adaptation: 1,500ms when focused, 5,000ms when tab is hidden via `document.visibilityState`.
  - Proper timer cleanup in `useEffect` hook teardown.
  - Optimistic updates preserve client-side submission state while background fetches reconcile.
</threat_model>

     ```typescript
     useEffect(() => {
       let intervalId: NodeJS.Timeout | null = null
       const startPolling = (intervalMs: number) => {
         if (intervalId) clearInterval(intervalId)
         intervalId = setInterval(() => {
           refreshInboxes()
           onRefresh()
         }, intervalMs)
       }

       // Initial start at 1.5s (active)
       startPolling(1500)

       const handleVisibilityChange = () => {
         if (document.hidden) {
           // Throttle to 5s in background
           startPolling(5000)
         } else {
           // Immediately resume 1.5s in foreground
           refreshInboxes()
           onRefresh()
           startPolling(1500)
         }
       }

       document.addEventListener('visibilitychange', handleVisibilityChange)
       return () => {
         if (intervalId) clearInterval(intervalId)
         document.removeEventListener('visibilitychange', handleVisibilityChange)
       }
     }, [refreshInboxes, onRefresh])
     ```
